# Antigravity Kickoff Prompt — Phase 0: Foundations, Data Model & Authentication

We're starting a new multi-vendor marketplace platform from scratch. This is Phase 0 of a longer build — the goal here isn't anything user-facing yet, it's the skeleton everything else depends on, so let's take our time getting the fundamentals right rather than rushing toward a demo.

The stack is Next.js using the App Router with server actions and API routes doing double duty as both frontend and backend, PostgreSQL as the database, and Prisma as the ORM sitting between them. I want the schema-first approach here — think of the Prisma schema file as living documentation of every relationship in this system, so let's be deliberate about getting the model right before writing much application logic on top of it. We're deploying to Vercel eventually, with a managed Postgres provider like Neon or Supabase, but for now let's just get everything running locally with a local Postgres instance and worry about hosting later.

Let's start with the roles. There are five kinds of people who'll use this platform: customers who browse and buy, vendors who own stores and sell, vendor staff who are scoped sub-accounts working under a vendor, riders who handle deliveries, and a superadmin who has platform-level control. I want all five of these scaffolded from the start, even though most of them won't have any real functionality yet — better to have the shape of the system in place early than to bolt on a new role type later and discover the base user model wasn't built to accommodate it.

Here's how I want identity structured. There should be one base `users` table that everyone shares regardless of role, and then each role gets its own extension table — `vendor_profiles`, `rider_profiles`, `staff_memberships`, and `customer_profiles` — that link back to that base user. The reason for this is that a single person could plausibly hold more than one role at once, like someone who's both a customer and a vendor on the same account, and I don't want to force separate logins for that. When someone logs in, check which profile extensions exist for their user id, and if there's more than one, show a lightweight chooser so they can pick which hat they're wearing for this session — the same interaction pattern we'll use later for vendors who run multiple stores.

On the subject of authentication, I want phone number to be the primary identifier, not email. Given the context this platform is built for, most people don't want to deal with email at all, so registration should just be phone number plus password. Email should be entirely optional and something a person can add later from their account settings if they want it, but it should never become a second way to log in or a parallel identity path — one canonical identifier, no ambiguity about which one someone's using. Passwords need to be hashed with bcrypt or argon2, never anything reversible, and I'd rather have a reasonable minimum length requirement than a bunch of forced complexity rules that just frustrate people signing up for what might be their first digital account.

For sessions, let's go with server-side, database-backed sessions stored in an httpOnly secure cookie rather than a JWT sitting in localStorage or a mobile-style access and refresh token pair. This is a web app, not something calling a separate mobile API, so there's no reason to take on the XSS exposure that comes with client-accessible token storage, and having sessions live in the database makes revocation trivial later — which matters a lot once we get to password resets. Speaking of which, don't build that flow yet in this phase, just make sure the sessions table and login mechanics are structured in a way that supports revoking all of a user's sessions cleanly when we do build it.

I also want you to think about failed login handling from the start — if someone fails to log in several times in a row, say five attempts, lock the account temporarily, something like fifteen minutes, rather than letting unlimited attempts through. This ties into a broader point I want you to take seriously in this phase: rate limiting and basic API hardening should exist from day one, not get added later once something's already been abused. Apply it especially to authentication endpoints, since those are the most attractive target.

Now for the core commerce schema. I want `stores` belonging to a vendor profile, `products` belonging to a store, and then `product_variants` and `product_images` underneath products for size, color, and photo handling. Categories should be a self-referencing table with a parent id, because I want a real hierarchical taxonomy, not a flat list — think of clothing having subcategories under it, not everything dumped into one level. For commerce itself, I want `carts` and `cart_items`, where each cart item is tagged with which store it belongs to, because carts here can span multiple vendors and we're going to need to split them at checkout into separate `orders` and then `sub_orders` — one sub-order per vendor per order — with `sub_order_items` underneath that. Payments and payment splits get their own tables too, `payments` and `paystack_splits`, since we're integrating with Paystack for payment processing including split payouts to vendor subaccounts. None of the checkout logic needs to work yet in this phase, I just want the tables to exist with the right foreign key relationships between them.

Beyond that, set up placeholder tables for warehouses and consignment stock and hub dropoffs, since we'll have a hub-based fulfillment model later, along with deliveries and rider assignments. Same for subscription plans and vendor subscriptions, since vendors will eventually be on a tiered subscription model. And for trust and access, I want KYC documents, vendor approvals, audit logs, and permission scopes tables scaffolded, plus OTP requests, SMS logs, and notifications for communications. None of these need real logic behind them yet — I just want the schema laid out now so later phases aren't retrofitting foreign keys onto tables that already have real data in them.

One thing I really care about for this phase: get the Paystack integration working end to end with a dummy sandbox charge before you build anything else on top of it. I don't want to discover three phases from now that the payment plumbing was broken the whole time — that's the kind of thing that's cheap to catch now and expensive to catch later.

Finally, let's set up testing and CI from the very start rather than treating it as something to add once the app already exists. I want unit tests around anything that's going to touch money or stock later — even though checkout logic isn't built yet, set up the testing infrastructure now so it's a non-issue to add tests as we build those features in the next phases. Get a basic CI pipeline running that runs tests and type-checking on every push, and make sure whatever managed Postgres provider we end up using actually has automated backups turned on — and let's actually test a restore once, since an untested backup isn't really a backup.

Let's talk through the schema together before you start generating migrations, especially around the identity and role structure, since that's the piece everything else depends on.
